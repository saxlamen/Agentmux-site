CLI エージェントとは、テキストでやり取りするコーディングエージェントのことです。Mac や Linux マシン、サーバーなど、あなたが所有するマシンのターミナル上で動きます。そこではあなた自身の権限を引き継ぎ、プロジェクト内の全ファイルを読み、任意のコマンドを実行し、その結果を読み取ります。エージェントがターミナルに棲むのは、この 3 つをすべて許すインターフェースが他にないからです。

「CLI」と聞くと、マウスもボタンもなくカーソルが点滅するだけの苦行のように思えるかもしれません。それでも Claude Code、Codex、Gemini CLI、OpenCode はすべてターミナルで動きます。開発者たちが懐古主義だからではありません。ターミナルだけが、ファイルへのフルアクセスとコマンド実行権限の 2 つを同時に与えてくれるからです。そして実行前にあなたへ確認を求めるのも、まさにその権限を持っているからです。

ボタンを取り払ったターミナルとは何か

ここでは 2 つのプログラムが重なって動いており、初心者はよく取り違えます。ターミナルは表示層であり、文字のグリッドを描画してキー入力を先へ渡します。その背後にあるのがシェル（zsh、bash、fish など）で、1 行のテキストを受け取って実行し、プログラムが書き出した結果を表示します。

この薄さこそが、エージェントが実際のプロジェクトを最初から最後まで動かせる理由です。エージェントが打つコマンドはあなたが打つコマンドそのものであり、エージェントが読むエラーもあなたが目にするエラーそのものです。

ターミナル画面から読み取る 3 つの要素

画面の中で意味を持つのは次の 3 か所だけで、残りは飾りです。

yuki@mini ~/projects/auth (main)
$ npm test

 ✓ src/session/refresh.test.ts  (6 tests)
 ✗ src/session/expire.test.ts > drops a session after expiry

     Tests  1 failed | 41 passed (42)

$ echo $?
1

プロンプトが最初の行です。自分が誰で、どのマシンにいて、どのディレクトリとブランチにいるかを示します。マシンが目の前にないとき、この行は単なる飾りではなくなります。SSH でログインしたあと、いま操作しているのが手元のノート PC なのか、切り忘れたサーバーなのかを見分ける手がかりになります。

標準出力（stdout）はプログラムが書き出したテキストです。もう 1 つのストリームである stderr はエラーや警告を分けて流し、本来の出力が読みにくくなるのを防ぎます。

終了ステータス。すべてのコマンドは終了時に整数を 1 つ残し、シェルはそれを $? として渡します。0 はプログラムが成功したと宣言したことを意味します。エージェントが読んでいるのは「1 failed」という文言よりもこの数値であり、1 が返ればループがまだ閉じていない合図になります。

インターフェースがエージェントの到達範囲を決める

ブラウザ上のエージェントは、あなたのパソコン内のファイルを 1 つも見られません。タブの中に閉じているためです。IDE プラグインは開いているファイルを見られますが、多くの場合は提案止まりで、git に触れたり、テストを走らせたり、パッケージを入れたりすることはできません。

CLI エージェントは、あなたが持つ権限をそのまま持ちます。リポジトリ全体を読み、git commit を実行し、テストスイートを走らせ、依存関係をインストールします。アクセス権限は 3 段階に分かれており、段階が上がるごとにリスクも増します。

  • 読み取り（Read）。ホームディレクトリ内のあらゆるファイル。.ssh の中の鍵も含まれます。
  • 書き込み（Write）。git 管理下のプロジェクトなら、誤った編集は git checkout 1 回で戻せます。管理外では誰も元に戻してくれません。
  • 実行（Execute）。あなたが打てるコマンドすべて。マイグレーション、force-push、パスを間違えた rm -rf も含まれます。

誰かが意図的にこの差を設計したわけではありません。ターミナルという仕組みにもともと付いてくる権限セットがそれであり、他のインターフェースはそこから一部を削っているだけです。

サンドボックスのエージェントには打てないコマンド

「実行権限」という言葉は抽象的です。画面上の行として並べるとこうなります。

npm test
npx vitest run src/session/expire.test.ts

git status --short
git commit -m "fix: expire sessions on the dot"

npm install date-fns@3
npm run build

psql "$DATABASE_URL" -f db/schema.sql
curl -sf localhost:8000/health | jq .db

ホスト型のサンドボックスには、これらを走らせる場所がありません。この psql はあなたのマシン上にしかないデータベースへ、アップロードされたことのない .env の URL を使って接続します。この npm install は .npmrc に書かれたプライベートレジストリから社内パッケージを引いてきます。これらの git コマンドは、あなたのリモート、フック、署名鍵を備えたクローン上で動きます。

サンドボックス内のエージェントはパッチを渡すことはできても、そのパッチが何を引き起こしたかを観測できません。自分の編集結果を確認できないエージェントは、タスクを完了させられません。

あなたが何も押さずに閉じるループ

あなたが「このバグを直して」と 1 行送ると、先ほどのようなコマンドが十数個、キーボードに触れないまま連続で実行されます。

  1. 失敗メッセージを grep で探し、3 つのファイルを読み、1 つを編集する。
  2. npm test を実行し、終了ステータスを読んで 1 を確認する。
  3. 1 つのテストケースに絞って再編集し、全体を流し直して 0 を得る。
  4. コミットし、ローカルにマイグレーションを適用し、壊れていたエンドポイントへ curl を投げる。

この一連の流れのどこにもクリックは要りません。同じエージェントをブラウザのタブや IDE プラグインに置くと、ステップ 2 で止まります。編集案は作れてもテストを走らせられないため、あなたがテストを実行して結果を教えてくれるのを待つことになります。あなたがテストランナーになってしまうのです。これはモデルの性能ではなく、権限の問題です。

ウィンドウよりバイトストリームのほうが価値がある理由

プログラムはターミナルウィンドウと一体化しているわけではありません。擬似端末（pseudo-terminal）という、両端を持つカーネルオブジェクトに繋がっています。片側からバイト列が入り、もう片側から出ていくだけで、ウィンドウとは今たまたま遠いほうの端を持っている存在にすぎません。この仕組みから 3 つの性質が生まれます。

  • 保存できる。npm test > build.log とすればテキストがファイルに書き出され、1 年後でも別のプログラムで読めます。GUI のキャンバスは絵であり、絵は記録になりません。
  • 連結できる。git ls-files | grep .env のように、あるプログラムの出力を次のプログラムの入力へ渡せます。
  • 移動できる。仕組みの定義上、両端が同じ場所にある必要はありません。tmux がセッションをサーバー側に置いておけば、あなたの画面は別の端末からアタッチ、デタッチ、再アタッチできます。

このガイドの要点は 3 つ目です。バイトストリームは転送し、保存し、再生し、別の場所から再接続できます。描画されたウィンドウにはそれができません。永続セッションも、SSH も、スマホ上の同じエージェントも、すべてこの 1 つの性質から導かれます。

フルアクセスの代償は何か

データベースをマイグレーションできる権限は、データベースを削除できる権限と同じです。だからこそエージェントは作業の途中で止まり、「このコマンドを実行しますか？」と尋ねます。確認を挟むのは安全のためです。

何も聞かずにすべてを実行するエージェントは、あなたの .ssh ディレクトリや本番データベースの扱いを推測だけで決めていることになります。確認プロンプトは第 2 段階（書き込み）と第 3 段階（実行）の境界線を引く場所であり、コマンドが確定していてまだ実行されていないその瞬間にしか引けません。

2 つの習慣でリスクの大半は抑えられます。1 つ目は要約ではなくコマンドそのものを読むこと。「ビルドキャッシュを整理します」は説明文にすぎず、実際に結果をもたらすのはその下の行です。

2 つ目はよく使う操作を一度だけ許可すること。テストの実行を 1 日 40 回聞かれるなら、npm test を通すルールを 1 つ書きます。

どうせ許可する確認に 10 秒かかっても大したことはありませんが、本番データベースへのコマンドを誤って許可すれば、1 日とリストア作業を失います。その比率があるからこそ AI 権限レビューがあります。ブラックリストで明らかに危険なものを止め、すでに信頼しているものは許可リストを通し、残りをモデルが判断します。

GUI のほうが適している場面

コードに対して行うすべての作業にターミナルが向いているわけではありません。次の作業はテキストでは明確に劣ります。

  • ライブデバッガ。ブレークポイントを置き、ループをステップ実行し、4 番目のフレームで変数の中身を見る作業。
  • 視覚的な作業全般。レイアウト、余白、わずかに違う色の調整。エージェントにスクリーンショットを説明させるより、自分で見たほうが速いです。
  • 大きな diff のレビュー。2,000 行を左右に並べて見る作業。エージェントが書いたコードであっても GUI でレビューする理由がここにあります。
  • まだ学習中の段階。エディタは間違えたトークンの下に線を引いてくれるため、スタックトレースの壁よりも速く学べます。

使い分けの基準は「自分がそこにいて操縦している」か「向こうで動いていて様子を見に来る」かです。机の上では IDE のほうが優れた道具であることが多く、CLI エージェントを最も使いこなしている人は両方を持っています。その役割分担については別の記事で詳しく書いています。

ターミナルはエージェントをあなたのマシンに置き、その出力はどこにでも運べる文字になります。つまりそのマシンは、あなたが今座っているマシンである必要がありません。別の場所からそこへ届くのが SSH の役目です。
