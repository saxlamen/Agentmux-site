让 agent 在你关掉手机后继续跑

tmux 是一个 terminal multiplexer：它让 terminal session 继续跑在你连进去的那台机器上，不是跑在你那条连接里面。对 AI coding agent 来说，这就是掉线之后 agent 能不能活下来的差别。SSH 连接迟早会断（手机锁屏、没信号），而掉线的 SSH 通常会把 agent 所在的 shell 一起杀掉。

你把手机收起来，SSH 隧道断了，agent 跟着死。这不是运气问题，是机制。

连接一断，kernel 会关掉你这次登录用的虚拟终端（pseudo-terminal），再对接在那个终端上的每个进程发送 SIGHUP（hangup）：你的 shell，也包括 shell 里面的 agent。进程除非自己处理过这个信号，否则默认就是终止，跑到一半的东西全部作废。SSH 只是连接走过的那条路，撑住 agent 的是那台机器，不是那条连接。

tmux 让 session 活在别的地方

tmux 在服务器上开一个 session。你的 agent 跑在那个 session 里面，不是跑在你那条一直会断的 SSH 连接里。

背后的机制是一个进程。你第一次输入 tmux，它就在你的账号底下启动一个后台程序，那是 tmux server，会一直活着。之后你开的每个 session 都属于它，每个 session 的虚拟终端也由它分配，不是由 sshd 分配。你的 agent 用的那个终端从此刻起归 tmux server 保管，跟手机那条连接没有关系。

下次连接掉线的时候，sshd 关掉的是它自己的虚拟终端，挂在上面的只有你的 tmux client。client 结束了，session 照样跑。

session、window、pane 各是什么？

这三个词常常被混着用，但只有第一个能保住你的 agent。后面每一段都用得到这三个词，所以先把它们分开。

词是什么对 agent 的意义
session 机器上一个有名字的工作场所，自带进程，由那台机器上的 tmux server 保管 掉线之后活下来的就是它。名字取一次，可以用好几个月
window 一个 session 里面的一个标签页，多数人一个 agent 开一个 你切走，它在后台照样跑
pane 一个 window 里面的分屏：左边 agent，右边测试或 git status 手机那一小块屏幕上同时看到两件事

第四个词也有用：client 就是当下正在看这个 session 的终端。一个 session 可以没有 client、有一个、或有好几个。零个不是错误，那就是 detach：session 照样在跑，只是没人看。

名字因此很重要。tmux new -s work 创建的 session 一周后还找得回来；不取名，tmux 就帮你编号，而“接回第 2 号”这件事过了三天就没有意义。

detach、attach，跟关掉电视是同一件事

把电视关掉，客厅里的画面没了。节目没停，一直在播。你回来打开，接的是同一个频道，从它播到的地方看下去。

tmux 把这两个动作叫 detach 和 attach：关窗、开窗。两个都碰不到机器上真正在跑的东西。

这个比喻会漏掉一件事，而且漏掉的部分对你有利。电视关着的时候画面就错过了，tmux 的 session 却把输出留了下来。一个小时后接回来，画面是它现在的样子，那一个小时打印出来的东西还在 scrollback 里，往上翻就看得到。

要下哪些命令？

先记这四个：

tmux new -s work          # 创建一个名叫 work 的 session
claude                    # 在里面启动 agent
tmux ls                   # 列出 session：work: 1 windows
tmux attach -t work       # 从任何终端再接上去看它

detach 不是命令，是按键。按 Ctrl-b，放手，再按 d。前面那个键是 prefix：tmux 收下它，下一个键才决定要做什么。另外两个第一周就会用到：

  • Ctrl-b d 就是 detach。终端变回普通的 shell，session 继续跑。
  • Ctrl-b c 开一个新的 window；Ctrl-b % 把一个 window 分割成两个 pane。

如果机器回你 tmux: command not found，解法在故障排查那一页。

连接掉线，agent 继续跑

你在地铁上断了信号，进电梯断一次，切 Wi-Fi 又断一次。每次都接回同一个 tmux session，掉线十次，agent 一次都没有被打断。它不知道你掉过线，因为它从头到尾就没活在你那条连接里。

手机上三个最令人担心的情况，其实是同一件事发生了三次：

  • 手机锁屏。系统把 app 暂停，连接跟着断开，什么信号都送不到 agent。它继续干活。
  • 二十分钟没信号。连接在后台安静地死掉，tmux client 跟着死，session 只是被 detach，内容一点没变。
  • 系统杀掉 app，或你往上一划。没了的是手机上的一个进程，session 从头就不在里面。在笔记本上关掉终端窗口，结果一模一样。

detach 不是暂停。你不在的时候，agent 继续读文件、改文件、花掉你的用量。这就是重点，所以走开之前先回它一句，或是先把它停掉。

两台设备可以同时看同一个 session 吗？

可以，而且没有什么魔法。多个 client 可以同时接在同一个 session 上。排队时从手机开工，到公司从笔记本接回同一个，你看到的是跑到一半的同一个画面，不是它的副本。

两边按的键都送进同一个程序，所以一次只有一个人打字。attach 不会移动 session：它留在创建它的那台机器上，所以手机和笔记本看到的内容一致。反过来也一样：你在笔记本的终端里手动开的 session，app 一样接得上，因为两边问的是同一台机器上的同一个 tmux server。

App 怎么处理这些 session？

Agentmux 用的就是上面那个区分：session 在机器上，连接只是去看它。手机这一侧的掉线是 detach，不是停止：重新连接，你回到同一个 session，而它已经跑得更远了。你在它的终端里手动下上面那些命令，结果一样，因为那是同一台机器上的同一个 session。

有两件杂事它帮你做掉了。机器上没有 tmux 时，app 会自己装，并判断你的机器用的是 apt、yum、dnf、pacman、apk 还是 brew。agent 装在 shell 看不到的地方时，app 会去查那个 PATH 问题，不会只丢给你一个毫无信息的画面。

持久 session 属于免费的 single-server 方案，上面这些功能都不用另外付费。设置页把整件事变成一份检查清单。

tmux 不做的事

tmux 只回答一个问题：这个进程会不会活得比你的连接久。其他它一概不管。

  • 服务器重启，所有 session 一起结束。它们存在 tmux server 的内存里，一次断电、一次自动更新，都会把 agent 一并带走。活下来的是已经写进硬盘的东西：改过的文件、做出的 commit、你停在哪个 branch。负责存档的是 git，不是 tmux。
  • 它不会还原 agent 已经跑过的命令。tmux 留住的是输出，文件不会自己回到之前的样子。
  • tmux kill-session -t work 真的会杀掉它。关掉最后一个 window，或是 agent 自己崩溃，结果一样。tmux kill-server 则把所有 session 一并带走，而且 tmux 不会先问你。
  • 它不会让机器保持醒着。整晚开着的 Mac mini，跟合上盖子就睡的笔记本是两回事：笔记本睡着，agent 跟着暂停，真的断电的话，session 就会整个消失。

两分钟就能验证整篇。SSH 进去，跑 tmux new -s work，启动 agent，按 Ctrl-b 再按 d，把连接整个关掉，然后跑 tmux attach -t work。画面还是同一个，已经跑得更远，上面有一个问题在等你回。

agent 现在能在你收起手机之后活下来。剩下一个问题：怎么从外面连进去，又不想在路由器上对公网开任何一个端口。Tailscale 回答的是这个。
