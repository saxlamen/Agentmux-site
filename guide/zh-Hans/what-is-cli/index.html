为什么最强的 coding agent 都住在终端里

CLI agent 是一个用文字跟你对话的 coding agent。它跑在你自己拥有的机器上，一台 Mac、一台 Linux 主机、或一台服务器，并沿用你在那台机器上的权限：读整个项目的文件、执行任何命令、把结果读回来。它住在终端里，因为没有别的界面能同时给你这三样。

“CLI”三个字听起来像惩罚：没有鼠标、没有按钮、只有一个闪烁的光标。可是 Claude Code、Codex、Gemini CLI、OpenCode 全都住在这里。做它们的人不是硬核，是因为终端给了 agent 两样别的界面给不了的东西：完整读写文件的权限，和执行命令的权限。也是因为这两样，它跑任何一条命令之前会先问你。

终端其实是两层程序叠在一起

这里有两个程序叠在一起，而初学者通常怪错那一个。终端是负责显示的那一层：它画出一格一格的字，把你的按键转出去，就这样。它后面的 shell（zsh、bash、fish）等一行文字出现，执行它，然后把程序写出来的东西打印在屏幕上。

就是因为薄到这个程度，agent 才操作得动。它打的每一行命令，跟你自己手动打的一模一样；它读到的错误信息，跟你看到的字不差。

屏幕上真正有意义的三样东西

这份指南后面每一篇都假设你会看屏幕。真正承载意义的是三样，其余都是杂音。

yuki@mini ~/projects/auth (main)
$ npm test

 ✓ src/session/refresh.test.ts  (6 tests)
 ✗ src/session/expire.test.ts > drops a session after expiry

     Tests  1 failed | 41 passed (42)

$ echo $?
1

提示符就是第一行。它告诉你四件事：你是谁、在哪台机器、哪个目录、哪个分支。机器不在你眼前的时候，这一行就不再是装饰。SSH 登录之后，它就是让你分清楚这是自己的笔记本、还是你忘记自己登进去过的那台服务器。

标准输出（stdout）是那个程序写出来的文字。第二条流 stderr 分开存放，真正的输出不会跟报错混在一起。

exit status。每一条跑完的命令都留下一个整数，shell 用 $? 交给你。0 表示程序正常结束。agent 读的就是这个数字。它读的不是“1 failed”那些字，而是那个 1，这说明它的工作还没完成，还会继续往下跑。

界面决定 agent 能碰到什么

网页版的 agent 看不到你电脑里的任何一个文件，它只活在浏览器标签页里。IDE 插件看得到你打开的文件，但通常停在“建议”这一步：它动不了 git，跑不了测试，更装不了包。

CLI agent 拿的是你自己那组权限：读整个 repo、下 git commit、跑测试套件、装依赖。访问分三层，风险一层比一层高：

  • 读。你家目录下的每一个文件，包含 .ssh 里的密钥。
  • 写。在 git 管着的项目里，改坏了一个 git checkout 就救得回来；项目之外，没有东西会帮你回滚。
  • 执行。任何你打得出来的命令，包括 migration、force push，还有指向错误路径的 rm -rf。

这个差距没有哪个厂商刻意设计过。选了终端当界面，这组权限就跟着来了。别的界面都扣掉了一部分，所以也做不了同样的事。

哪些命令是沙盒里的 agent 跑不了的？

“执行权限”是一个抽象的说法，点头之前先把它还原成屏幕上的行：

npm test
npx vitest run src/session/expire.test.ts

git status --short
git commit -m "fix: expire sessions on the dot"

npm install date-fns@3
npm run build

psql "$DATABASE_URL" -f db/schema.sql
curl -sf localhost:8000/health | jq .db

这些命令搬到别人的云端沙盒里，要跑在哪里？那行 psql 连的是只存在于你机器上的数据库，用的 URL 来自一个从来没上传过的 .env。那行 npm install 从你 .npmrc 里写明的私有 registry 拉内部包。那些 git 动作跑在本地的仓库里，里面有你的 remote、hook 和 signing key。

沙盒里的 agent 可以写一份 patch 给你，但看不见那份 patch 造成了什么结果。看不见一次 edit 的结果，就没办法把工作做完。

不用你按键，agent 就能自己跑完一轮

你丢一句“把这个 bug 修好”。接着是十几行同样的命令，而你的手不用碰到键盘：

  1. 它 grep 那条错误信息，读三个文件，改一个。
  2. 它跑 npm test，读 exit status，看到 1。
  3. 它缩到那一个失败的用例，再改一次，整组重跑，拿到 0。
  4. 它 commit，在本地把 migration 套上去，再 curl 那个坏掉的 endpoint。

整条链上没有一个按钮需要按。换成浏览器标签页或 IDE 插件，它在第二步就停下：它能产出那个 edit，却跑不了测试，于是等你去跑，再等你把结果回报给它。到最后你变成了测试执行器。这是权限的问题，不是模型强弱的问题。

为什么字节流比一个窗口值钱？

你屏幕上那个终端窗口不是程序住的地方。程序接在一个 pseudo-terminal 上，那是 kernel 里一个有两端的对象：一端写进去字节，另一端就出来字节，而你的窗口只是当前接在另一端的显示层。从这个定义跟着来三件事：

  • 可以保存下来。npm test > build.log 把那串文字写进文件，一年后另一个程序还能读它。GUI 的画布是一张图，图本身不是记录。
  • 可以接起来。git ls-files | grep .env 把一个程序的输出，变成下一个程序的输入。
  • 可以搬走。那个定义没有一句话说两端必须在同一个地方。tmux 把 session 搁在服务器上，你的屏幕接上去、detach、再从另一台设备接回来。

第三点才是这篇的重点。字节流可以被转向、保存起来、重播，也可以从别的地方接回去；渲染好的窗口做不到。之后要讲的持久 session、SSH、在手机上接回同一个 agent，每一件事都是从这个性质来的。

完整访问要付什么代价？

让 agent 能对数据库做 migration 的那个权限，也能把那个数据库删掉。它知道这一点，所以会在工作做到一半时停下来问：“要跑这条命令吗？”那个 prompt 不是胆小。一个什么都不问就直接跑的 agent，随时可能误删你的 .ssh 目录或生产环境数据库。prompt 画的是第二层跟第三层之间那条线，而且只能在那个时刻画：命令已经知道了，还没有执行。

两个习惯挡掉大部分风险。读命令本身，不要读摘要：“我要清掉 build cache”是一段描述，只有它下面那一行才有后果。同一类只批一次：一天四十次要你批准跑测试，就用一条规则让 npm test 直接通过。

这里的代价不对称。一个你本来就会批准的 prompt 花你十秒。一个你误批准、跑在生产数据库上的命令，花你一天和一次 restore。就是这个比例让 AI 自动权限审查存在：先 blacklist，再 allowlist，剩下的交给模型判断。

什么时候 GUI 更好

终端不是对代码做任何事的正确界面。下面这些事情，用文字做就是比较差：

  • 实时 debugger。设 breakpoint、单步走过那个循环、在第四个 frame 看一个变量。
  • 任何视觉的东西。排版、间距、一个差一点点的颜色。叫 agent 描述一张截图，比你自己看一眼差得多。
  • 读一个大的 diff。两千行并排着看。所以就算代码是 agent 写的，你多半会在 GUI 里 review 它的工作。
  • 还在学的时候。编辑器在你写错的那个 token 下面画一条线，比一整墙的 stack trace 教得快。

这条分界分的不是熟练跟懒惰，分的是“你在场、你在开”跟“它在跑、你去看”。坐在桌前，IDE 常常是更好用的那个工具，而把 CLI agent 用到最好的人，两边都留着。那条分工线怎么画，自己就是一篇。

终端把 agent 放进你自己的机器，而它的输出是可以住在任何地方的字符。所以那台机器不必是你正坐着的这一台。从别的地方连过去，是 SSH 的工作。
