Keep the agent running after you put your phone away

tmux is a terminal multiplexer: it keeps a terminal session running on the machine you connect to, rather than inside the connection you came through. For an AI coding agent, that is the difference between surviving and dying. SSH connections drop — a locked phone, a lost signal — and a dropped SSH normally kills the agent's shell.

You put your phone away, the SSH tunnel drops, and the agent dies with it. That is mechanics, not bad luck.

When the connection goes, the pseudo-terminal your login was using is closed. The kernel sends SIGHUP — hangup — to every process attached to it: your shell, and the agent inside it. Unless a process goes out of its way to handle that signal, the default is to terminate. Everything half-finished is thrown away. SSH was only the road the connection travelled on, and nobody meant it to hold the agent up.

tmux lets the session live somewhere else

tmux opens a session on the server. Your agent runs inside that session, not inside the SSH connection that keeps dropping.

The mechanism is a process. The first time you type tmux, it starts a background program — the tmux server — that stays alive under your user account. Sessions belong to it, and each one gets its pseudo-terminal from that process, not from sshd.

So when the connection goes, sshd closes its own pseudo-terminal, and only your tmux client is attached to it. The client exits. The session does not notice.

What is a session, a window, a pane?

Three nouns, used as one, and only the first keeps your agent alive.

WordWhat it isWhat it means for an agent
session A named place to work on that machine, holding its own processes The thing that survives. Name it once
window A tab inside a session; most people give each agent one Switch away and it keeps running
pane A split inside a window: agent left, tests right Two things visible on a phone screen

A fourth word: a client is the terminal looking at a session. Zero clients is normal — a detached session, still running, nobody watching.

Names matter. tmux new -s work can be found again a week later; an unnamed session is just a number.

Detach and attach are the same as turning off a television

Switch a TV off and the picture in your living room is gone. The broadcast never stopped. Turn it back on and you are on the same channel, wherever it has got to by now.

tmux calls those two actions detach and attach — close the window, open it again. Neither touches what is running on the machine.

The analogy hides one thing, in your favour. A television off learned nothing while off; a tmux session kept its output. Attach an hour later and you can read the hour you missed, scrollback and all.

Which commands do I actually type?

Four to start with:

tmux new -s work          # make a session named work
claude                    # start the agent inside it
tmux ls                   # list sessions: work: 1 windows
tmux attach -t work       # look at it again, from anywhere

Detach is a key press, not a command. Press Ctrl-b, let go, then press d. That first key is the prefix: tmux takes it, and the next key says what to do. Two more are worth learning:

  • Ctrl-b d — detach. The terminal becomes an ordinary shell again; the session runs on.
  • Ctrl-b c makes a new window; Ctrl-b % splits a window into panes.

If the machine answers tmux: command not found, the fix is on the troubleshooting page.

What this means for an agent

You lose signal on the train. Again in a lift. Again switching Wi-Fi. Attach to the same tmux session each time and you can drop ten times without the agent being interrupted once. It does not know you ever disconnected. It was never living inside your connection.

The three phone-side cases people worry about are one event three times over:

  • The phone locks. The system suspends the app, the connection is torn down, nothing reaches the agent. It kept working.
  • No signal for twenty minutes. The connection dies quietly, the tmux client with it, the session left detached and untouched.
  • The app is killed or swiped away. A process on the phone is gone; the session was never inside it. Close a laptop's terminal window and tmux does the same.

Detach is not pause. While you are gone the agent keeps reading files, editing them, and spending your quota — which is the point, and the reason to answer a waiting prompt before you walk off.

Can two devices watch the same session?

Yes, and it is not a party trick. Several clients can attach to one session at once. Start the job from the phone in a queue, attach from the laptop at work, and you are looking at the same screen mid-sentence — not a copy.

Keys from either device go to the same program, so one person types at a time. Attaching moves nothing: the session stays on the machine that made it, which is why phone and laptop agree. A session you started by hand in a laptop terminal is there for the app too.

How the app handles these sessions

What tmux does not do

tmux answers one question — will this process outlive my connection — and leaves the rest alone.

  • A reboot of the server ends every session. They live in the tmux server's memory, so a power cut or an unattended upgrade ends the agent with them. What survives is what reached the disk: files changed, commits made, the branch you were left on. Git is the save file, not tmux.
  • It does not undo a command the agent already ran. A command that ran has run. tmux kept the output; it does not roll back the files.
  • tmux kill-session -t work really does kill it. So does quitting the last window, or the agent crashing. tmux kill-server takes every session with it. None of that asks first.
  • It does not keep the machine awake. A Mac mini that stays on is a different case from a laptop that sleeps when the lid shuts — and a machine that powers off loses the session.

Two minutes proves the article. SSH in, run tmux new -s work, start an agent, press Ctrl-b then d, close the connection, and run tmux attach -t work: the same screen, further along, one question waiting.
