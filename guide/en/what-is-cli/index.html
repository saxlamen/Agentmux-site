Why the strongest coding agents live in the terminal

A CLI agent is a coding agent you talk to in text. It runs in a terminal on a machine you own — a Mac, a Linux box, a server — and inherits your permissions: read every file in the project, run any command, read the result back. Agents live in terminals because no other interface grants all three at once.

"CLI" still reads like a punishment: no mouse, no buttons, one blinking cursor. Yet Claude Code, Codex, Gemini CLI and OpenCode all live there. Not because their makers are purists: the terminal grants what no other interface does — full filesystem access and permission to execute. The same grant is why it asks before running anything.

What is a terminal, once you strip the buttons away?

Two programs are stacked here, and beginners blame the wrong one. The terminal is the display: it draws a grid of characters and forwards your keystrokes. The shell behind it — zsh, bash, fish — waits for a line of text, runs it, and prints what that program wrote.

That thinness is why an agent can drive one end to end: every command it types is one you would have typed, every error it reads the one you would have seen.

Three things you read off a terminal screen

Three things carry the meaning; the rest is noise.

yuki@mini ~/projects/auth (main)
$ npm test

 ✓ src/session/refresh.test.ts  (6 tests)
 ✗ src/session/expire.test.ts > drops a session after expiry

     Tests  1 failed | 41 passed (42)

$ echo $?
1

The prompt — that first line — says who, on which machine, in which directory, on which branch. It stops being decorative once the machine is not in front of you: after an SSH login it is how you tell your laptop from a server you forgot you opened.

Standard output, or stdout, is the text the program wrote. A second stream, stderr, keeps the complaints apart from the real output.

The exit status. Every command leaves one integer behind, handed over as $?. Zero means the program claims success. That is the line an agent reads — the 1, not the words "1 failed": proof its loop is not closed.

A capability boundary, not a question of looks

A browser agent cannot see a single file on your computer. It lives in a tab. An IDE plugin sees the files you have open, but it is usually confined to suggesting — no touching git, no running the tests, and certainly no installing packages.

A CLI agent holds the permissions you hold: it reads the whole repo, runs git commit, runs the suite, installs dependencies. Three tiers come with that, and the risk climbs:

  • Read. Every file in your home directory, .ssh keys included.
  • Write. Under git, a bad write is a git checkout away. Outside a tracked project, nothing rolls it back.
  • Execute. Anything you could type, including a migration, a force-push, an rm -rf pointed at the wrong path.

No vendor designed this gap to please anyone: it is the permission set that comes with the terminal, and every other interface withholds part of it.

Which commands can it run that a sandboxed agent cannot?

"Execution rights," in lines on a screen:

npm test
npx vitest run src/session/expire.test.ts

git status --short
git commit -m "fix: expire sessions on the dot"

npm install date-fns@3
npm run build

psql "$DATABASE_URL" -f db/schema.sql
curl -sf localhost:8000/health | jq .db

Where would those run inside a hosted sandbox? That psql connects to a database that exists only on your machine, using a URL from a .env file that was never uploaded. That npm install pulls an internal package from a private registry named in your .npmrc.

A sandboxed agent can write you a patch but cannot observe what the patch did — and an agent that cannot see the result of an edit cannot finish the task.

The loop that closes without you pressing anything

You say "fix this bug." A dozen of those lines follow, hands off the keyboard:

  1. It greps for the failing message, reads three files, edits one.
  2. It runs npm test, reads the exit status, sees 1.
  3. It narrows to one case, edits again, reruns the whole suite, gets 0.
  4. It commits, applies the migration locally, curls the endpoint that was broken.

Nothing in that chain needed a click. In a browser tab or an IDE plugin it stalls at step two: it can produce the edit but cannot run the suite, so it waits for you to run it and report back. You have become the test runner — a permission problem, not a model-quality one.

Why is a byte stream worth more than a window?

A terminal window is not where the program lives. The program is attached to a pseudo-terminal — a kernel object with two ends. Bytes go in one end and out the other; your window is whoever holds the far end right now. Three things follow.

  • It can be saved. npm test > build.log writes that text to a file, which a program can read a year later. A GUI's canvas is a picture, not a record.
  • It can be chained. git ls-files | grep .env feeds one program's output into another's input.
  • It can be moved. Nothing says the two ends must be in the same place. tmux parks the session on the server; your screen attaches, detaches, and attaches again from another device.

That third one is the payload. A byte stream can be redirected, stored, replayed, and reattached from somewhere else; a rendered window cannot. Persistent sessions, SSH, the same agent on a phone: everything else in this guide follows from that property.

What does full access cost you?

The permission that lets an agent migrate your database lets it delete one, which is why agents stop mid-task and ask: "Run this command?" That prompt is not timidity. An agent that ran everything without asking would be taking your .ssh directory and your production database on faith. It marks the line between tier two and tier three, drawn once the command is known.

Two habits cover most of it. Read the command line, not the summary: "I'll clean up the build cache" is a description, and only the line under it has consequences. Approve once per category: asked forty times a day to run tests, let npm test through on a rule once.

A prompt you were going to approve costs ten seconds. One allowed wrongly, against a live database, costs a day and a restore. That ratio is what AI Permission Review exists for: blacklist first, allowlist second, a model's judgement for the rest.

When a GUI is genuinely the better tool

A terminal is not the right interface for everything you do to code. These are strictly worse in text:

  • A live debugger. A breakpoint, one step through the loop, a variable inspected at frame four.
  • Anything visual. Layout, spacing, a colour that is almost right. Describing a screenshot is a worse version of looking at one.
  • Reading a large diff. Two thousand lines side by side — why you review an agent's work in a GUI even when the agent wrote it.
  • Still learning. An editor underlining the exact token where you went wrong teaches faster than a stack trace.

The split is not skill against laziness. It is "you are here and driving" against "it is running and you are checking in". At a desk an IDE is often the better instrument; the best users keep both. That division of labour is its own article.

The terminal gives an agent your machine, and its output is characters that can live anywhere — so the machine need not be the one you are sitting at. Getting there from elsewhere is SSH's job.
