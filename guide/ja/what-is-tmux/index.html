スマホを閉じた後もエージェントを動かし続ける

tmux はターミナルマルチプレクサです。接続先のマシン上でターミナルセッションを動かし続けます。

AI コーディングエージェントにとって、これは生き残るか死ぬかの違いになります。スマホがロックされたり電波が切れたりすると SSH 接続は切断され、切断された SSH は通常エージェントのシェルごと終了させてしまうためです。

スマホをしまうと SSH トンネルが切れ、エージェントも一緒に死にます。これは通信環境の問題ではなく、OS の仕様による動作です。

接続が切れると、カーネルはログイン時に使われていた擬似端末（pseudo-terminal）を閉じます。そしてそこに繋がっていたすべてのプロセス（シェルとその中のエージェント）へ SIGHUP（ハングアップ）シグナルを送ります。このシグナルを意図的に捕捉しないプロセスは既定で終了し、カーネルはやりかけの状態をすべて破棄します。SSH は接続が通ってきた道にすぎず、エージェントを生かし続ける仕組みではありません。

tmux はセッションをサーバー側に置く

tmux はサーバー上にセッションを開き、SSH 接続から切り離されたそのセッションの中でエージェントを動かします。

仕組みは 1 つのプロセスです。最初に tmux と打つと、tmux server と呼ばれるバックグラウンドプログラムがあなたのユーザーアカウント下で起動して常駐します。セッションはそのプロセスに属し、各セッションの擬似端末は tmux サーバーが管理します。

接続が切れると、sshd は自分の擬似端末を閉じますが、そこに繋がっていたのは tmux クライアントだけです。クライアントは終了しますが、セッション自体は動き続けます。

session、window、pane の違い

tmux では 3 つの異なる概念に 3 つの名詞を使い、その中でエージェントを生かし続けるのは最初の 1 つだけです。

用語何かエージェントにとっての意味
session そのマシン上で自分のプロセス群を保持する名前付きの作業場 切断に耐えて残る単位。最初に 1 回名前を付ける
window セッション内のタブ。多くの人はエージェントごとに 1 つ開く 別のタブに切り替えても裏で動き続ける
pane ウィンドウ内の分割領域（左にエージェント、右にテストなど） スマホ画面に 2 つの出力を並べて見られる

4 つ目の言葉として、client（クライアント）はセッションを覗いているターミナル自身を指します。クライアント数がゼロのセッションは正常な状態です。それはデタッチされた状態で、今も動いていて、誰も画面を見ていないだけです。

名前を付けることは重要です。tmux new -s work で作ったセッションは 1 週間後でもすぐに見つかりますが、名前を付けないセッションは番号を調べ直さなければなりません。

デタッチはテレビの電源を切るようなものか

テレビの電源を切ればリビングの映像は消えますが、放送自体は止まりません。もう一度電源を入れれば、その時点まで進んだ同じチャンネルが映ります。

tmux ではこの 2 つの操作を detach（デタッチ） と attach（アタッチ） と呼びます。ウィンドウを閉じ、また開くだけです。どちらもマシン上で動いている処理には一切触れません。

ただしこの例えには 1 つ隠れた違いがあり、しかもあなたに有利に働きます。テレビは消している間の内容を覚えていませんが、tmux セッションは出力を保持しています。1 時間後にアタッチすれば、スクロールバックして見逃していた 1 時間分のログをすべて読めます。

実際に打つコマンド

まずは次の 4 つから始めます。

tmux new -s work          # work という名前のセッションを作る
claude                    # その中でエージェントを起動する
tmux ls                   # セッション一覧を見る: work: 1 windows
tmux attach -t work       # どこからでも同じ画面に再接続する

デタッチはキー操作で行います。Ctrl-b を押して離し、次に d を押します。最初のキーは プレフィックス と呼ばれ、tmux がそれを受け取って次のキーで何をするか判断します。あと 2 つ覚えておくと便利です。

  • Ctrl-b d でデタッチします。ターミナルは通常のシェルに戻り、セッションは動き続けます。
  • Ctrl-b c で新しい window を作り、Ctrl-b % で window を左右の pane に分割します。

マシンが tmux: command not found と返してくる場合の対処は、トラブルシューティングページに載っています。

回線が切れてもエージェントは中断されない

電車で電波を失い、エレベーターでまた切れ、Wi-Fi の切り替えでもう一度切れます。毎回同じ tmux セッションにアタッチし直せば、10 回切れてもエージェントは 1 回も中断されません。エージェントは最初からあなたの接続の中にいなかったため、切れたことすら気づきません。

スマホでよく心配される 3 つのケースは、実は同じ現象を 3 通りの言葉で説明しているだけです。

  • スマホがロックされる。OS がアプリを一時停止し、接続が切れてエージェントに届かなくなります。それでも作業は続きます。
  • 20 分間圏外になる。接続は静かに死に、tmux クライアントも一緒に終了します。セッションはデタッチ状態のまま無傷で残ります。
  • アプリを終了するかスワイプで消す。スマホ側のプロセスが消えただけで、セッションは最初からその中にはいません。ノート PC のターミナルウィンドウを閉じたときと tmux の挙動は同じです。

デタッチは何も一時停止しません。あなたが離れている間もエージェントはファイルを読み、編集し、利用枠を消費し続けます。それこそが目的であり、だからこそ席を離れる前に「待機中の確認プロンプト」があれば先に答えておく必要があります。

2 台の端末で同じセッションを見られるか

見られます。特別な仕掛けも要りません。複数のクライアントが同時に 1 つのセッションへアタッチできます。駅で並びながらスマホでジョブを始め、職場のノート PC からアタッチすれば、コピーではなく文の途中のまったく同じ画面が目の前に現れます。

どちらの端末から打ったキーも同じプログラムに届くため、入力は一度に 1 人だけです。アタッチしても何かが移動するわけではありません。

セッションはそれを作ったマシンに留まり続けるため、スマホとノート PC の画面が一致します。ノート PC のターミナルで手動起動したセッションにも、アプリからそのまま入れます。

アプリがセッションを扱う仕組み

Agentmux もまったく同じ分離の上に作られています。スマホ側の切断は単なるデタッチにすぎず、再接続すればさらに進んだ状態の同じセッションに戻ります。アプリ内のターミナルで上記のコマンドを打っても、やはり同じセッションです。

アプリはさらに 2 つの手間を肩代わりします。マシンに tmux が入っていなければ、apt、yum、dnf、pacman、apk、brew のどれを使うマシンかを判別して自動でインストールします。エージェントがシェルから見えない場所にある場合は、その PATH 問題を調査します。

永続セッションは無料の単一サーバー枠に含まれているため、ここには課金要素はありません。セットアップページではこれをチェックリストに落とし込めます。

tmux がやらないこと

tmux が解決するのは「プロセスが接続断を生き延びるか」という 1 点だけで、それ以外には手を出しません。

  • サーバーが再起動すると全セッションが終了する。セッションは tmux サーバーのメモリ上にあるため、停電や自動アップデートによる再起動が起きればエージェントも終了します。残るのはディスクに書き出されたもの（変更されたファイル、作ったコミット、いたブランチ）だけです。作業状態を保存するのは Git の役割です。
  • エージェントがすでに実行したコマンドは取り消せない。tmux はそのコマンドの出力を保持しますが、ファイルを元に戻す機能はありません。
  • tmux kill-session -t work は本当にセッションを殺す。最後の window を閉じたり、エージェントがクラッシュしたりしても終了します。tmux kill-server は全セッションを道連れにし、tmux は実行前に確認しません。
  • マシン自体を起こし続けるわけではない。電源を入れっぱなしの Mac mini と、蓋を閉じるとスリープするノート PC は別物です。電源が落ちたマシンではセッションも消えます。

この動作を確かめるのに 2 分しかかかりません。SSH で入り、tmux new -s work を実行し、エージェントを起動し、Ctrl-b のあと d を押し、接続を切ってから tmux attach -t work を実行してみてください。少し先に進み、あなたへの質問を 1 つ抱えて待っている同じ画面が戻ってきます。

これでスマホをしまってもエージェントが生き延びるようになりました。残る問題はあと 1 つ、インターネット全体にポートを開けずに外から入る方法です。その答えが Tailscale です。
