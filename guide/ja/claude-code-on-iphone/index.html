iPhoneやiPadからClaude Codeを使う

使えます。ただし Claude Code 本体は自分の Mac や Linux マシン上で動き、iPhone で動くわけではありません。接続先のマシンで「リモートログイン」を有効にし、Tailscale 経由で繋いで、名前付きの tmux セッションの中で claude を起動します。

iPhone が担うのはターミナル画面の表示とキー入力だけです。画面をロックしても、バックエンドのエージェントは動き続けます。この構成で押さえるべきポイントは、回線切断後も処理を生き残らせる方法、SSH 経由でコマンドが見つからない理由、移動中に権限確認プロンプトへどう答えるかの 3 点です。

Claude Code は iPhone の中で動いているのか

Claude Code は、あなたが所有するマシンのディスク上にあるプログラムです。シェルから起動され、そのマシンのファイルシステム経由でプロジェクトを読み、git やテストを実行し、編集結果を同じディレクトリへ書き戻します。

iPhone とマシンの間でやり取りされるのは、送信するキー入力と返ってくる文字列の 2 つだけです。エージェントは iPhone にインストールされず、リポジトリのコピーも転送されません。iPhone は別のコンピュータで動いているセッションの画面を描画しているだけです。

  • iPhone 側にあるもの。キー入力、表示画面、親指の操作。画面をロックしたりアプリを終了したりすると表示は止まりますが、それだけです。
  • マシン側にあるもの。プロセス本体、編集中のファイル、テスト実行、そしてエージェントが読み込んで判断したすべてのコンテキスト。画面が暗くなっても一切影響を受けません。

ここから 2 つの前提が導かれます。1 つ目は、マシンが起動してネットワークに繋がり続けている必要があること（閉じたままのノート PC は何も動かせません）。2 つ目は、壊れたり失くしたりしたときに買い替えやすいのは iPhone の側だということです。

この順番で整える 3 つの準備

1 つでも抜けると機能しないため、次の順番通りに設定してください。

  1. マシンへの入り口。Mac なら「システム設定」→「一般」→「共有」→「リモートログイン」をオンにします。Linux なら SSH サービス（sshd デーモン）を有効にします。
  2. プライベートネットワークで接続する。マシンと iPhone の両方に Tailscale をインストールして同じアカウントでサインインし、MagicDNS 名または 100.x アドレスで接続します。192.168.1.23 のような LAN アドレスはモバイル回線に出た瞬間に使えなくなるため避けてください。また、ルーターでポート 22 を開放するとスキャンボットにマシンを晒すことになります。
  3. 名前付きの tmux セッションと、その中でのエージェント起動。
tmux new -s work     # セッションに名前を付ける
claude               # その中で起動する

別のネットワークにいる iPhone からは次のように繋ぎます。

tmux ls              # 動いているセッションを確認
tmux attach -t work  # その画面にアタッチ

名前を付けることには意味があります。引数を省いた tmux attach は直近のセッションを選ぶため、意図したセッションに繋がるとは限りません。tmux が未導入の場合は、Agentmux が自動でインストールします。

なぜ素の SSH ウィンドウではエージェントが死ぬのか

tmux を使わずに SSH でログインし、claude を実行してから iPhone をポケットに入れて画面をロックしたとします。

iPhone からのパケットが止まると接続がタイムアウトして切断されます。sshd はその接続に紐づいていた擬似端末（PTY）を閉じ、カーネルはその端末に繋がっていたすべてのプロセス（シェルと、その中の Claude Code）へ SIGHUP を送ります。どちらも既定の動作として終了するため、20 分かけて読み込んだコンテキストごと編集の途中で消滅します。

アプリを開きっぱなしにしても解決しません。Wi-Fi の切り替え、電波の途切れ、うっかり押した Ctrl-C で同じことが起きます。tmux はセッションをマシン側へ移すため、接続が切れてもウィンドウが閉じるだけでプロセスは生き残ります（詳しい仕組み）。すでに動き始めたプロセスを後から tmux に移すことはできないため、作業を始める前にセッションの中へ入れておく必要があります。

スマートフォンからの作業は実際どんな感覚か

スマートフォンに向いているのは「一度に 1 つの判断」です。ちょうどエージェントの作業サイクルもその単位で回ります。エージェントが計画を提示し、こちらは承認するか一文だけ修正を返します。「シリアライザは触らないで、エクスポート処理で使っている」といった 2 行の指示を返したら、またポケットにしまえます。

最初にぶつかる壁はソフトウェアキーボードです。バッククォート、パイプ、引用符、バックスラッシュ、チルダは 2 階層奥にあり、~/src/auth/session.ts を打つだけでも時間がかかります。1 セグメント打ち間違えるだけでやり直しです。長文のプロンプトは見た目以上に推敲しづらいため、メモアプリで下書きしてから貼り付ける人も多くいます。

画面の狭さが顕著に出るのは diff です。2 ファイルで 40 行の変更があると 6 インチ画面では 3 画面分のスクロールになり、行が折り返されると変更が行末なのか途中なのか判別しにくくなります。iPad を横向きにすれば、同じ diff も折り返さずに読めます。

すぐ元が取れる習慣が 1 つあります。テスト実行などのログが大量に出る作業用に 2 つ目のセッションを分け、エージェントの確認プロンプトが流れて埋もれないようにすることです。

tmux new -s tests -d    # -d でデタッチ状態で開始
tmux attach -t tests    # 様子を見てからデタッチ

エージェントは自分の権限確認に自動で答えられるか

Claude Code は思いついた操作をすべて無条件に実行するわけではありません。コマンドを実行する前（設定によってはファイルを編集する前）に停止し、「このコマンドを実行してよいか？」と尋ねてきます。この停止で作業が止まるため、人間しか答えられない状態だと待ち時間がボトルネックになります。

AI 自動権限レビューは、この権限プロンプトだけを対象に画面を読み取り、キーを提案または入力します。まずブラックリストが危険なコマンドを弾き、一致したものは必ずあなたへ渡します。次に許可リストが信頼済みのコマンドを端末内で即決します。どちらにも当てはまらないものだけが AI 判定（許可／拒否／保留）に送られ、拒否と保留はあなたへ戻されます。最後にセッションのモードに応じて、キーを提案するだけか自動押下するかが決まります。

遠く離れていても責任が消えるわけではありません。モバイル回線越しに許可したコマンドは、あなたの .env や鍵、共有リポジトリがあるマシン上で実行されます。しかも AI 判定が見ているのは現在の画面だけで、エージェントがそこに至った推論の経緯までは見えません。

まずは提案のみの「アドバイザー」モードから始め、毎日許可しているコマンドを許可リストに登録してください。電波や集中力が怪しいときは、押す前に画面を読むことが大切です。ブラックリストがあるのは「すべて許可」が危険な既定値だからで、ホームディレクトリを狙った rm -rf はどこから許可しても被害が変わりません。

Terminal では動くのに SSH 越しだと claude: command not found になる

同じマシン、同じアカウントなのに、Terminal では claude が起動し、SSH 経由では claude: command not found と表示される。リモート環境が壊れたように見えますが、これは導入時にもっともよくある失敗です。

npm でのインストールや nvm が管理する Node バージョンは、対話的ログインシェルだけが読み込む起動ファイルに PATH を追記します。一方、ssh host claude のように単発コマンドを実行する接続は非対話シェルを起動するため、その起動ファイルを読み込まず PATH が通りません。

確実に動く応急処置は、PATH に頼らず絶対パスを使うことです。普段動いている Terminal で次を実行します。

which claude
# /Users/you/.nvm/versions/node/v20.11.0/bin/claude

表示された絶対パスをそのままエージェントコマンド欄に設定するか、セッション内で入力します。ただし nvm で Node のバージョンを切り替えるとパスが変わる点に注意してください。シェルやディストリビューションごとの恒久的な直し方は、トラブルシューティングで解説しています。

一晩中動かしたままにできるか

スリープしないマシン上のセッションなら一晩中動かせます。夜 11 時にリファクタリングを投げて、朝コーヒーを飲みながら結果を確認する使い方も可能です。ただし、邪魔をする要因が 3 つあります。

マシンが起きている必要がある。Mac がアイドルスリープに入るとネットワークインターフェースも止まるため、リモートログインがオンでも応答できなくなります。ノート型なら「システム設定」→「バッテリー」、デスクトップ型なら「省エネルギー」で自動スリープを延長または無効にし、「ネットワークアクセスによるスリープ解除」があればオンにしてください。

再起動するとセッションは消える。tmux は OS の再起動をまたいでセッションを復元しないため、ソフトウェアアップデートで自動再起動がかかると終了します。夜作業を離れる前に commit しておけば、最悪でも失うのは数時間分で済みます。

止まっているように見えて待っているだけのことがある。アタッチして画面を見てください。素のシェルプロンプトに戻っていればプロセスが終了（完了または異常終了）しており、数行上に理由が出ています。

質問のプロンプトで止まっているなら、追加コストなしで何時間もあなたの返事を待っている状態です。ロック画面の表示だけではどちらも同じに見えるため、確認して対処するのは後者だけです。

スマートフォンでやること、机でやること

スマートフォンから机の前で
内容を読んだ上で権限プロンプトに答える想定外の変更を含む diff をレビューする
エージェントが示した 2 案から方針を選ぶ複数ファイルにまたがる設計変更を判断する
短い diff を 1 つ読んで commit・push する長い diff や初めて開くファイルを読む
2 つ目のセッションでテスト実行を見守るテスト失敗の原因をデバッグする
寝る前に次のタスクを投げる細部まで正確な指示が必要なプロンプトを書く
回線が 10 回切れても再アタッチする接続設定や背後の PATH 問題を直す

必要な条件は 3 つだけです。眠らないマシン、名前付きのセッション、そして安全な接続経路。どれかが欠けている場合は、セットアップウィザードで 3 つの質問に答えると手順チェックリストが作れます。
