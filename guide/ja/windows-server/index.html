Windows PCもそのままサーバーになる

はい。Agentmux は Linux レイヤーを挟まずに、ネイティブの Windows PC へ SSH で直接接続できます。Windows 10 または 11 に同梱されている OpenSSH Server を有効にし、他のサーバーと同じように接続先へ追加するだけで、PowerShell ターミナル、psmux による永続セッション、そしてコーディングエージェントが利用できます。

以前は「手前に WSL2 を立てる」必要がありましたが、理由は欠けていたプログラムが 1 つだけあったためです。tmux には Windows 版がなく、スマホの回線が切れてもエージェントを生かし続けるには tmux が不可欠でした。現在では Windows 向けに書かれた互換プログラムがその穴を埋めるため、WSL2 だけが入り口ではなくなりました。

Windows PC 側で必要な 2 つの条件

1 つ目は SSH の入り口です。Windows 10 と 11 にはオプション機能として OpenSSH Server が含まれており、管理者権限の PowerShell で次のコマンドを実行して有効化します。

# PowerShell（管理者として実行）
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Start-Service sshd
Set-Service -Name sshd -StartupType Automatic

インストーラーは OpenSSH-Server-In-TCP という受信ファイアウォール規則を追加します。より厳しいファイアウォール環境にある場合は、まずこの規則を確認してください。

2 行目でサービスを今すぐ起動し、3 行目で再起動後も自動起動するように設定します。Windows PC は更新プログラムで自動的に再起動することがあるため、Mac 以上にこの設定が重要です。

2 つ目はマルチプレクサです。Agentmux は接続時にホストの OS を自動判別し、Windows ホストであればアプリ側の挙動を自動で切り替えます。

内部コマンドには PowerShell を使い、Windows のドライブパスを扱い、tmux の代わりに psmux を使います。切り替えスイッチを探す必要はなく、ログインシェルが PowerShell でも cmd.exe でも動作します。

なぜ psmux を使うのか

psmux は tmux をモデルにしたコマンドライン（セッション、ウィンドウ、ペイン、send-keys、capture-pane）を持つ独立したプログラムです。tmux.exe というエイリアスも配置されるため、普段の操作感もそのまま使えます。Agentmux は psmux、pmux、tmux.exe の順に探し、見つかったものをそのまま使うため、すでに入っている環境を壊すことはありません。

psmux は tmux の移植版ではありません。Agentmux はバージョン文字列を鵜呑みにせず、そのプログラムが実際に何を返すかを検証し、確認できない機能は使いません。後述する違いは、この実地検証の結果に基づいています。

そもそもなぜマルチプレクサが必要なのか仕組みを知りたい場合は、tmux の役割を参照してください。接続が切れるとシェルが SIGHUP を受け取り、マルチプレクサなしではエージェントも道連れで終了します。

psmux が入っていない場合どうなるか

Agentmux が自動でインストールします。まず winget install -e --id marlocarlo.psmux を試し、次に Scoop、次に cargo install psmux と、存在するパッケージマネージャーを使って導入し再接続します。スマホ側からコマンドを打つ必要はありません。

この 3 つがどれも入っていない環境だけが手動対応になります。その場合、アプリは「Neither winget, scoop, nor cargo was found on the Windows server. Install psmux manually, then reconnect.」とそのまま表示します。

簡素化された Windows 構成や winget を削除したサーバーが該当します。バイナリを入手して PATH の通った場所へ置き、再接続してください。

導入後は同じフォルダに psmux.exe、pmux.exe、tmux.exe の 3 つの名前で配置されます。そのマシン上で tmux と打てば psmux が起動し、psmux --version を実行すると自身のバージョンの前に tmux 3.4.0 と表示されます。二重にインストールされているわけではありません。

Windows セッションでできること

  • セッションの永続化。一覧表示、デタッチ状態での作成、アタッチ、名前変更、単体削除、一括削除が使えます。Ctrl-b d で PowerShell プロンプトへデタッチでき、Agentmux のタブは開いたまま残ります。
  • プロジェクトフォルダでのエージェント起動。C:\Users\you\src\app のような Windows パス（スペースを含むパスも可）から Claude Code、Codex、または任意のコマンドを起動できます。
  • 画面状態の読み取り。ペインが許可プロンプト待ちか、作業中か、アイドルかをペイン自体から判定でき、AI 自動権限レビューも Windows 上でキーの提案と自動送信の両方に対応しています。
  • 主要シェルの両対応。Windows PowerShell 5.1 と PowerShell 7、パスワード認証と鍵認証、ドライブレター、UNC パス、スペースを含むフォルダ名に対応しています。

Linux マシンとの違い

  • ファイル操作は SFTP 経由。閲覧、編集、転送は SFTP サブシステム経由で行います。OpenSSH 側で SFTP が無効になっている場合は、エラーメッセージで通知します（ターミナル機能自体は SFTP 不要です）。
  • ファイルブラウザで制限される 2 つの操作。スクリプトの実行と Git 操作は意図的に拒否されます。Windows ホスト上でシェルエラーを出してユーザーに解釈させるのを防ぐためです。
  • ペインの作業フォルダ表示なし。psmux には pane_current_path がないため、アプリは各ペインがどのフォルダにいるかを取得できず、実行中プログラム欄には PowerShell と表示されます。また、その表示の更新間隔も Linux より遅くなります。
  • 添付ファイルの保存先は temp フォルダ。送信した画像やファイルは、Linux や Mac では /tmp に、Windows では Windows の temp フォルダに保存されます。ターミナルへ入力されるパスはいずれも実際の保存先です。
  • Windows はあくまで「接続先」。Windows 上で動く Agentmux クライアントアプリはありません。手元の操作端末が Windows で、エージェントが別のマシンにある場合は、この記事の内容は当てはまりません。

それでも WSL2 を使うべきケース

理由は 1 つだけ残っています。apt や systemd、スラッシュ区切りのパスが使える Linux ユーザーランドが欲しい場合です。WSL2 の内部では、このガイドの Linux 向け手順がすべてそのまま使えます。

ただし 3 つの落とし穴は残ります。WSL2 は NAT 配下の仮想マシンで動くため、netsh interface portproxy でポート転送するか .wslconfig でミラーネットワークを有効にしないと外部から sshd に届きません。

また、最後のプロセスが終了すると数秒でディストリビューションが停止するため、常時稼働にはタスクスケジューラの設定が必要です。さらに古い環境では systemd が既定でオフになっており、ウィザードのサービス起動コマンドがそのまま通らないことがあります。

まとめると、Linux のプログラムが必要なら WSL2 を選び、その PC 自体をサーバーとして使いたいならネイティブ構成を選んでください。仮想マシンを起こし続ける手間も、再起動のたびにアドレスが変わる心配もありません。

入り口が開き、セッションも消えなくなりました。残るはスマートフォンから入力するアドレス、つまり外出先からそのアドレスへ安全に接続できるかという点です。
